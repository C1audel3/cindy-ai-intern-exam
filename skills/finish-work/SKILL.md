# 收工

用户说“收工”时，按以下顺序执行。把本次任务的已知起点提交、用户指定范围和对话中已完成的提交作为审阅边界；不要把整个仓库的旧问题算成本次改动。如果起点不明确，先用当前工作区与 `HEAD` 比较，并从对话和提交记录核对本次已提交的改动；仍无法确定的范围在结果中说明，不能声称已审完未知提交。

1. **跑测试。** 先读项目的 `AGENTS.md`、README 或包脚本中与改动相关的验证要求，选择覆盖本次改动的最小有效测试集并实际运行。记录命令、退出码和关键结果。若没有可运行的测试或依赖缺失，记录尝试过的命令和阻碍，不写“测试通过”。发现本次改动造成的失败时，修复后重新运行相关测试；无法修复时保留失败证据。
2. **从头到尾复核改动。** 用 `git status --short` 确定文件范围；逐项查看本次已提交差异、暂存差异、未暂存差异和新文件全文，连同删除文件、配置与文档一起看。可用 `git diff --check` 查格式问题，但不能用它代替内容审阅。检查需求是否完成、变更之间是否一致、是否误带无关文件或敏感数据。对明确属于本次任务的问题直接修正；改动后重新复核受影响部分。
3. **清查临时调试内容。** 在本次改动涉及的代码和配置中搜索 `console.log`、`debugger`、临时 `print`、硬编码测试值、假 token、调试开关和临时文件；结合上下文逐条判断，保留确属产品日志或正式测试夹具的内容。删除或改正真正的临时残留，并复核改动；如果改了运行逻辑，重跑相关测试。不要为了“清零搜索结果”删除有用途的代码。
4. **给出简短摘要。** 说明本次改了什么、实际执行的测试及结果、改动与调试内容复核结果，以及仍未解决的失败或验证限制。结论只覆盖实际检查过的范围。除非用户已另外要求，不因“收工”自行提交、推送、发布或清理用户文件。

固定的是以上四步的顺序、必须实际运行并记录测试、必须覆盖所有变更状态、必须报告未完成项。由 AI 根据仓库规则和改动风险选择测试命令，判断搜索命中是否为临时残留，并决定最小的修复方式。
